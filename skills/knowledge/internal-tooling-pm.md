## Core Knowledge

### Internal Customers Are Different

Your users didn't choose your product. They were told to use it (or it was installed on their machine). This changes everything:
- **No acquisition funnel.** Everyone is already "acquired." The challenge is activation and retention.
- **No pricing signal.** You can't tell if people value the tool by whether they pay for it. You need usage data.
- **Captive but resentful.** If the tool is mandatory but bad, people will use it minimally and complain. Compliance is not adoption.
- **Direct feedback channel.** Your users are in Slack. You can watch them use the tool. You can ask them questions. This is an enormous advantage — use it.

### The "IT Mandate" Trap

Internal tools fail when they're treated as IT projects: mandated from above, specced in isolation, measured by deployment rather than usage. A well-designed adoption strategy is explicitly not this — it's adoption-first, measured by real usage. Hold that line.

### Friction Is the Enemy

Every click, every configuration step, every "contact IT to set up" is friction that kills adoption. The golden path ([device management] pushes config, [drive sync] provides context, the user opens the AI tool, everything works) is exactly right. The measure of platform success is: how many steps between "I want to use the tool" and "I'm using the tool effectively"? The answer should be zero.

### Prioritisation for Internal Platforms

When prioritising the platform backlog:
1. **Unblock the critical path.** What's preventing the highest-priority department or use case from working? Fix that first.
2. **Reduce the highest-volume friction.** What support request do you get most often? Eliminate it.
3. **Enable the champion.** What does the most active champion need to be more effective? Give them that.
4. **Scale what works.** A use case that works for one department but could work for three is higher priority than a new feature for one department.

### Measuring Internal Tool Success

- **Adoption:** DAU, WAU, MAU, and the ratios between them (stickiness)
- **Depth:** Are people doing meaningful work, or just checking in? Message count, session length, MCP usage
- **Satisfaction:** NPS is noisy for internal tools. Better: "would you notice if this tool disappeared?" and "what would you go back to doing without it?"
- **Support load:** Are support requests going down over time? Is the tool self-serve?
